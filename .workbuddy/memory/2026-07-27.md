## 根因定位：跳转失效的真正原因 = total_lines 估算偏小（非滚动竞态）
- **用户洞察**："是不是因为 1525201 行后的数据没有显示导致的" → 一语中的
- **真实根因**：`local.rs` 的 `open_local` 用「仅采样文件前 8KB」估算 `total_lines`，若开头恰为几条超长行，估算值严重偏小（如实际 1300万行被估成 ~152万行）
- **连锁反应**：
  1. 前端 `.viewer-spacer` 高度 = `total_lines × 22`，占位不足
  2. 浏览器将 `scrollTop` 上限 clamp 到估算末尾（~第152万行）
  3. 跳转 `scrollTop = 13279825 × 22` 被截断 → 停在第152万行附近
  4. 而 `search_local` 是**全文件扫描**，能找到第13279825行匹配 → 点击却跳不到
- **注意**：此前 v0.1.4/v0.1.6 的"滚动竞态"修复方向有误，真正的 bug 是占位高度不够

## 修复方案（双层）
- **后端** `src-tauri/src/local.rs`：
  1. `estimate_total_lines()` 改为**多区域采样**（开头/1/4/1/2/3/4/末尾 各 8KB，取平均行长推算），偏差远小于单点采样
  2. `total_lines: u64` → `Cell<u64>`，`read_local` 读到文件末尾时自校正为精确值（`f.total_lines.set(last_line)`）
  3. `open_file` 命令读取改为 `f.total_lines.get()`
- **前端** `src/components/LogViewer.tsx`：
  1. 新增 `maxKnownLine` state，从 `readLines` 返回的 `LogLine.line` 取最大值
  2. `effectiveTotal = max(total, maxKnownLine + PAGE*2)`，占位高度与 endIdx 均用它
  3. 跳转 effect 中 `setMaxKnownLine(targetLine + PAGE/2)`，确保占位在跳转前已扩展
- 验证：`tsc --noEmit` + `cargo check` 均通过（仅原有 harmless warning）

## 二次修复：v0.1.8 仍卡在 1525202 行 — 两个被遗漏的 bug
- **现象**：v0.1.8 发布后，手动滚动仍停在第 1525202 行，跳转也只到该行
- **遗漏 bug 1（前端 React 反模式）**：`setMaxKnownLine` 写在 `setCache` 的 updater 函数内部，
  React 不允许在另一个 setState 的 updater 内调用 setState → 增长从未生效 → 占位高度锁死在估算值
- **遗漏 bug 2（跳转目标被截断）**：`targetLine = Math.min(jump.line, total)` 把跳转目标按**偏小估算 total** 截断，
  跳到 13279825 行实际变成跳到 1525202 行；且 `preloadEnd` 也按 total 截断 → 后端根本没去读目标区域
- **遗漏 bug 3（DOM scrollTop 先被旧高度截断）**：跳转时同步设 `containerRef.scrollTop` 发生在占位高度更新前，
  被旧（短）spacer 高度 clamp
- **修复**（`src/components/LogViewer.tsx`）：
  1. `setMaxKnownLine` 移到 `setCache` updater 之外（先算 maxLine，再分别更新两个 state）
  2. `effectiveTotal = max(total, maxKnownLine) + PAGE*4`（始终保留余量）
  3. 跳转不再按 total 截断：`targetLine = max(1, jump.line)`；`preloadEnd = targetLine + PAGE/2`（不截断）
  4. 先 `setMaxKnownLine` 扩展占位，再用 `requestAnimationFrame` + setTimeout 兜底设置 DOM scrollTop，避免被旧高度截断
  5. `handleScroll` 中接近底部时自动 `setMaxKnownLine` 扩展（无限滚动增长），手动滚动不再卡死

## 卡在 1525202 行的真正根因（v0.1.9 后第三次反馈，终于定位）
- **根因：浏览器 DOM 元素最大高度硬上限**。Chromium/WebView2 的 LayoutUnit 上限 ≈ 33,554,432px。
  spacer 高度 = 行数 × 22px，33,554,432 ÷ 22 = **1,525,201.45** → 第 1525202 行正好是物理极限。
  超过后 spacer 高度被浏览器**静默 clamp**，scrollTop 物理上滚不过去 —— 与前端状态逻辑无关，
  所以 v0.1.8/v0.1.9 两次修复全部无效。1525202 这个精确数字就是铁证。
- **排查确认**：remote.rs 的 remote_read（tail -n +N | head）和 remote_search（grep -n）后端均无行号上限，问题纯在前端 DOM。
- **修复方案（LogViewer.tsx 重写坐标系统）**：
  1. spacer 物理高度封顶 `MAX_SPACER_PX = 30,000,000px`（安全余量）
  2. 引入物理/虚拟双坐标系：`scale = (虚拟高度-视口)/(物理高度-视口)`，行数不超限时 scale=1 完全退化为原逻辑
  3. 滚动：物理 scrollTop × scale → 虚拟位置 → 行号；跳转：虚拟目标 ÷ scale → 物理 scrollTop
  4. `forcedScrollTop` 改为 `forcedVirtualTop`（虚拟坐标），彻底不受物理上限影响
  5. `rowsOffset = physicalScrollTop - (virtualScrollTop - startIdx*ROW_H)` 保证行块贴合视口
  6. scale 用 scaleRef 供 rAF/setTimeout/onScroll 回调读取最新值，避免闭包过期
- 验证：tsc --noEmit 通过、vite build 通过（待用户确认后发布）
- **经验**：虚拟滚动组件必须假设总高度可能超过 ~3300 万 px（约 152 万行 @22px），一开始就要做高度封顶+比例映射。
